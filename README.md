### 📋 Що зробити

**1. Замініть поля-переліки на `enum`.** Усе, що в ЛР1 було `String` із фіксованим списком значень (`status`, `type`, `category`, `zone`…), стає окремим `enum` у пакеті `ua.<домен>.model` — з тими самими константами, що в профілі.

Щонайменше один `enum` має власне поле і конструктор:

```java
public enum RoomType {
    SINGLE(1.0), DOUBLE(1.6), SUITE(2.5), DELUXE(3.2);

    private final double priceFactor;

    RoomType(double priceFactor) {
        this.priceFactor = priceFactor;
    }

    public double getPriceFactor() {
        return priceFactor;
    }
}
```

Перевірка «чи значення є в списку допустимих» після цього стає непотрібною — чому саме, спитаю на захисті.

**2. Переробіть у `record` класи, поля яких не повинні змінюватися після створення.** Класи, стан яких змінюється, лишаються класами — у профілі позначено, які саме поля змінювані.

Валідація переїжджає в компактний конструктор:

```java
public record Room(int roomNumber, RoomType type, double pricePerNight) {
    public Room {
        HotelUtils.requireInRange(roomNumber, 1, 999, "roomNumber");
        HotelUtils.requirePositive(pricePerNight, "pricePerNight");
    }
}
```

Пакет `util` лишається як був — і `ValidationHelper`, і `FormatHelper`, і `<Домен>Utils`.

**3. Видаліть із `record`-ів усе, що тепер генерує компілятор:** геттери, `equals`, `hashCode`, `toString`.

**4. Напишіть два `switch`-вирази** — саме вирази (Java 14+), зі стрілками і поверненням значення, а не `switch`-інструкції. Обидва живуть у `<Домен>Utils`, поруч із обчислюваними методами з ЛР1:

- перший — по вашому `enum`, **без `default`**: перелічіть усі константи;
- другий — там, де в домені є вибір поведінки: коефіцієнт ціни, доступна дія за статусом, категорія знижки, текст для користувача.

**5. Оновіть `Main`.** Показати треба:

1. створення `record`-обʼєкта і звернення до його компонентів;
2. `enum` у роботі: перебір `values()`, доступ до власного поля константи, `valueOf` на неправильному рядку в `try/catch`;
3. обидва ваші `switch`-вирази;
4. `record`, створений з невалідними даними → `IllegalArgumentException` із компактного конструктора;
5. два однакові `record`-обʼєкти: `equals` і `hashCode` — без жодного рядка, написаного вами;
6. вивід `record` через згенерований `toString()`.

### 🎤 Захист

5 хвилин, 3–4 питання по **вашому** коду й по діффу у вашому PR. Орієнтовно:

- Чому `record` не може успадкувати `BaseEntity`? Що ви зробили з `createdAt` і чому саме так?
- Які класи ви залишили класами і за яким правилом?
- Що саме компілятор згенерував за вас у `record`? Як виглядає його `equals`?
- Чому в компактному конструкторі не пишуть `this.field = field`?
- Чому `switch`-вираз по `enum` можна писати без `default`, а по `String` — ні? Що станеться, якщо завтра в `enum` додати константу?
- Чим `switch`-вираз відрізняється від `switch`-інструкції? Що таке провалювання (fall-through) і чому його тут немає?
- Куди поділася перевірка «значення є в списку допустимих» після переходу на `enum`?
- Чи є у вашому `record` поле-масив або змінюваний обʼєкт? Наскільки він тоді справді незмінний?
